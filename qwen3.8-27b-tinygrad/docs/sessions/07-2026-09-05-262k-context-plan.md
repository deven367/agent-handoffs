# Handoff — tinygrad 262K-context serving plan (2026-09-05)

## Goal

Serve Qwen3.8-27B with its native `262144`-token context through tinygrad on `node-lair`. Distinguish two milestones:

1. **Fits and accepts the context** — model starts and safely enforces the shared prompt/completion window.
2. **Operationally useful** — a long prompt prefills in reasonable time. Current CUDA token-at-a-time prefill does not meet this milestone.

## Exact context-memory constraint

The loaded model has 64 active blocks: 48 recurrent blocks and 16 full-attention blocks. GGUF metadata relevant to KV storage:

- native context: `262144`
- KV heads: `4`
- key/value head dimension: `256`
- cache dtype in `TransformerBlock._init_state`: FP16

One FP16 KV slot therefore requires:

```text
2 (K,V) * 16 layers * 4 KV heads * 262144 tokens * 256 values * 2 bytes
= 17,179,869,184 bytes
= 16 GiB
```

Q8_K_XL projects to at least `29.5 + 16 = 45.5 GiB`, before the larger RoPE table and runtime temporaries. The L40S exposes only ~44.99 GiB. **Q8_K_XL plus FP16 KV cannot safely serve 262K on this card.**

The measured Q4_K_M runtime is ~16.0 GiB at context 512. With the same FP16 KV, its projected total is ~32 GiB and should fit with ~13 GiB headroom.

## Decision ladder

Use the first acceptable route; do not implement quantized KV speculatively.

### Route A — L40S + Q4_K_M (recommended shortest path)

Use:

```text
/data/user/demistry/Qwen3.8-27B-OBLITERATED-Q4_K_M.gguf
```

This route needs launcher and boundary work, not a new cache format. It changes weight precision/model variant relative to Q8_K_XL.

### Route B — Q8_K_XL + 64 GB or larger GPU

Keep the current Q8 model and FP16 KV. Add the context option and validate on a 64/80/94 GB GPU. This is the shortest route if Q8_K_XL is mandatory and hardware can change.

### Route C — Q8_K_XL + L40S

Implement quantized KV consumed directly by attention. Q8 KV payload is ~8 GiB plus scales, projecting total near 38 GiB. Do not dequantize the whole cache per token; that recreates peak memory and bandwidth costs. This is a substantial kernel project and starts only if both Q8_K_XL and the L40S are hard constraints.

## Execution plan

### Phase 1 — Make context explicit and enforce its boundary

1. Add to `/u/demistry/agent-handoffs/Makefile`:

   ```make
   TG_CTX ?= 262144
   ```

2. Pass `--max_context $(TG_CTX)` in `serve-tg`.
3. For Route A, set or override `TG_MODEL` to the available Q4 path above.
4. In `tinygrad/llm/serve.py`, validate the whole requested window:

   ```text
   prompt_tokens + requested_completion_tokens <= model.max_context
   ```

   The current check rejects only `prompt_tokens >= max_context`; it does not reserve completion space.
5. Keep one request slot. `Transformer` owns one mutable KV/SSM cache; concurrent independent contexts are not supported and full-context cache memory would multiply per slot.

Acceptance:

- `make serve-tg TG_CTX=262144` reports `max context 262144`.
- A request whose prompt plus completion exceeds 262144 gets HTTP 400 before generation.
- A request ending exactly at the boundary is accepted.
- `make stop-tg` releases all GPU memory.

### Phase 2 — Prove memory before attempting a huge prompt

Run the smallest allocation smoke first:

```bash
cd /u/demistry/tinygrad-src
PYTHONPATH=. python3 -c '
from tinygrad.llm.model import Transformer
m,_ = Transformer.from_gguf("/data/user/demistry/Qwen3.8-27B-OBLITERATED-Q4_K_M.gguf", max_context=262144)
m.warmup()
print("FULL_CONTEXT_WARMUP_OK")
'
```

Record both tinygrad `GlobalCounters.mem_used` and `nvidia-smi` peak. Do not start with Q8_K_XL on the L40S; the exact FP16 KV calculation already exceeds capacity.

Acceptance:

- Cold warmup completes without allocator retry/OOM.
- Peak stays below 44 GiB, leaving at least ~1 GiB operational headroom.
- Short-prompt output matches the same model at context 4096; context capacity must not alter logits.

### Phase 3 — Measure the actual prefill blocker

Current `Transformer.generate` forces recurrent non-AMD models to `chunk_size=1`. This prevents the 32-token scratch OOM but makes 262K prefill impractical: every prompt token streams model weights again.

Before editing kernels, measure prompt sizes 512, 4096, and 32768 and report prefill tokens/s separately from decode tokens/s. Extrapolation is not acceptance for 262K, but it establishes which graph dominates.

Investigate the prior chunked-prefill regression at the shared source:

- CUDA quant GEMV kernels allocate partial output shaped roughly `(tokens, out_features, chunks, 32)`.
- Symbolic `tokens<=32` uses the maximum shape; individual buffers can be hundreds of MB.
- Determine why those buffers are held outside TinyJit's reusable memory plan. Instrument `held_bufs`/`all_tensors` in `tinygrad/engine/jit.py` temporarily; remove instrumentation afterward.
- Prefer making scratch planner-reusable over lowering the global chunk size.
- Preserve the all-lanes-active reduction invariant documented in `docs/kernels-explained.md`; lane-0 gating previously broke CUDA shuffle semantics.

Only after bounded scratch is proven:

1. Test chunk sizes `2, 4, 8, 16, 32` with peak VRAM recorded.
2. Numerically compare logits/tokens to `chunk_size=1`.
3. Restore chunked CUDA prefill at the largest size with safe headroom.
4. Profile generic CUDA attention at 32K/128K. Port flash attention only if profiling proves it is the next bottleneck or materializes an unsafe score buffer.
5. Revisit an NVIDIA fused `gated_delta_prefill` only after scratch is fixed. The previous experiment compiled but did not solve OOM and had no numerical A/B validation, so it was reverted.

Acceptance:

- Chunked and scalar prefill produce matching logits within the existing model tolerance and identical greedy tokens.
- No warmup or 32K prefill OOM.
- Prefill throughput improves materially over `chunk_size=1`; report measured pp and tg separately.

### Phase 4 — Quantized KV only for Route C

Current cache allocation is in `TransformerBlock._init_state`:

```python
Tensor.zeros(2, batch, n_kv_heads, max_context, head_dim, dtype=dtypes.half)
```

Required design constraints:

1. Store K and V in packed int8 with explicit per-group scales.
2. Quantize only newly written positions.
3. Consume packed cache in tiled attention; dequantize tiles in registers/shared memory, never the full history.
4. Keep cache reset/prefix-reuse behavior correct for the hybrid recurrent model.
5. Start with one slot and batch size one.

Verification against FP16 KV at context 4096:

- finite logits
- greedy-token identity over a representative sequence
- report maximum absolute logit error and correlation
- cache-prefix reuse and divergent-prompt reset produce the same result as a cold run

Then repeat memory and boundary tests at 262144. Target peak: under 42 GiB on the L40S, leaving several GiB for compilation and attention temporaries.

## Long-context verification matrix

Run in order; stop at the first failure and fix the source rather than suppressing it.

| Context | Purpose |
|---:|---|
| 512 | regression against already verified behavior |
| 4096 | current server baseline and FP16/Q8-KV A/B reference |
| 32768 | prefill throughput and attention-memory profile |
| 131072 | scaling check; catches score-buffer growth |
| 262144 minus completion budget | final native-context proof |

For the final request, reserve completion tokens. A 262144-token prompt leaves zero room to generate.

Record for each size:

- prompt tokens, requested completion tokens
- prefill tok/s and decode tok/s separately
- tinygrad tracked memory and `nvidia-smi` peak
- first generated token or logit checksum
- cold run versus cache-prefix reuse

## Do not repeat

- Do not remove the recurrent `chunk_size=1` guard before peak-memory and numerical checks.
- Do not add allocator cache flushing; `LRU=0` did not change the OOM.
- Do not blame KV at context 512; it was only ~32 MiB there. The warmup regression was symbolic GEMV scratch.
- Do not claim Q8_K_XL contains Q3_K/Q8_K tensors. Its observed distribution is Q8_0, BF16, and F32.
- Do not launch concurrent full-context slots on one L40S.
