# Priority 2 — Q4_K_M practical 262K prefill

## Goal

Make native-context Qwen3.8-27B prefill operationally useful in tinygrad on the L40S. Use the already-fitting Q4_K_M model as the low-memory control, then transfer proven changes to priority-one Q8_K_XL.

This plan is second priority. Do not delay Q8 quantized-KV fitting work unless a prefill change is a direct prerequisite.

## Starting state

- Model: `/data/user/demistry/Qwen3.8-27B-OBLITERATED-Q4_K_M.gguf`.
- Full `max_context=262144` warmup succeeds.
- Measured full-context usage: `34,385,001,532 B` in tinygrad counters; `36904 MiB` by `nvidia-smi` while serving.
- Short API request at context 262144 succeeds.
- tinygrad CUDA/NV recurrent generation forces `chunk_size=1`.
- Measured pp512: 28.5 tok/s; steady decode: ~28.7 tok/s.
- Same llama.cpp model: pp512 2532.5 tok/s with FP16 KV and 2503.4 tok/s with Q4_0 KV; decode ~38.9 tok/s.
- The previous `chunk_size=32` attempt OOMed because symbolic custom-GEMV partial buffers reached hundreds of MB per call and were held across the graph.

## Required outcome

- Chunked prefill no longer OOMs Q4_K_M.
- Chunked and scalar prefill produce matching logits within existing tolerance and identical greedy tokens on the validation prompt.
- pp512 improves by at least 8× before further kernel work is justified.
- Decode remains within 2% of the current ~28.7 tok/s.
- Peak remains below 42 GiB at full configured context.
- Changes transfer to Q8_K_XL only after Q8 quantized KV gives enough memory headroom.

## Phase 1 — Prove the scratch owner

Do not start by porting attention or delta kernels. First confirm why symbolic GEMV scratch escapes reuse.

Relevant files:

```text
tinygrad/llm/kernels/nv.py
tinygrad/llm/kernels/nv_q4k.py
tinygrad/llm/kernels/nv_q6k.py
tinygrad/llm/kernels/nv_q5k.py
tinygrad/llm/kernels/nv_iq4xs.py
tinygrad/engine/jit.py
tinygrad/schedule/memory.py
```

The custom kernels allocate partial output approximately as:

```text
(tokens, out_features, chunks, 32) float32
```

At symbolic `tokens<=32`, maximum-shape buffers include roughly:

- 356.5 MB for common FFN projections
- 209.7 MB for attention-sized projections
- 125.8 MB for SSM projections

Investigation:

1. Reproduce with Q4_K_M, context 512, temporary chunk size 32.
2. Use `DEBUG=2` to identify allocation growth and kernel order.
3. Temporarily instrument TinyJit's `held_bufs` calculation: report each held buffer over 32 MiB, size, dtype, and the live Tensor path retaining it.
4. Compare `all_tensors`-reachable buffers against buffers accepted by `memory_planner`.
5. Reduce to one representative Q4_K and Q6_K Linear before using `DEBUG=3/4`.
6. Remove all instrumentation after capturing evidence.

Acceptance: name the exact retention edge and show that releasing or planning it removes the corresponding peak. A size coincidence is not proof.

## Phase 2 — Make scratch reusable with the smallest change

Preferred order:

1. Build custom-kernel scratch as raw buffer UOps not registered as long-lived Tensor roots, if that lets the existing planner alias them.
2. If raw UOps do not solve retention, narrow the Tensor lifetime so scratch is not included in `held_bufs`.
3. Only if planner reuse cannot work, redesign the kernel reduction to use a smaller output.

Preserve the CUDA reduction invariant:

- all 32 lanes must stay active through warp shuffle
- do not gate the whole warp on lane 0
- the earlier lane-0 store predicate produced invalid shuffle results

Apply the proven fix consistently to every NVIDIA quant kernel using the same partial layout. Do not create a second scratch-management convention.

Retained checks:

- existing Q8_0, Q4_K, Q5_K, Q6_K, IQ4_XS sweeps
- symbolic token counts 1, 2, 3, 7, 16, 31, 32
- multiple `chunks` values
- no change in static decode output

## Phase 3 — Re-enable chunked prefill incrementally

Keep the production guard while experimenting. Test chunk sizes:

```text
2, 4, 8, 16, 32
```

For each size record:

- cold compile peak
- warm pp512 and pp4096
- generated first-token/logit checksum
- steady decode speed
- `GlobalCounters.mem_used` and peak `nvidia-smi`

Compare each against `chunk_size=1` on identical tokens. Restore CUDA/NV chunking only at the largest size that:

- stays below 42 GiB on Q4 at max context
- passes numeric A/B
- does not regress decode by more than 2%

Do not lower the global default merely to hide a memory bug. A smaller temporary chunk is acceptable only with a measured ceiling documented in code.

## Phase 4 — Fuse the recurrent scan if it is now the bottleneck

Qwen3.8 has 48 recurrent blocks. The prior NVIDIA `gated_delta_prefill` experiment compiled and executed but:

- did not solve the original OOM
- had no numerical A/B
- was reverted

After scratch reuse enables chunking, profile again. Port the fused scan only if recurrent operations dominate pp time.

Requirements:

1. Keep AMD behavior unchanged.
2. Use NVIDIA warp reduction primitives.
3. Compare fused versus scalar recurrent outputs and final logits across token counts 1, 2, 7, 16, 32.
4. Test initial state reset, prefix extension, and divergent-prompt reset.
5. Record pp improvement independently from GEMV improvements.

## Phase 5 — Profile attention before replacing it

CUDA/NV currently uses generic `scaled_dot_product_attention`; the custom cache flash-attention path is AMD-only.

Measure at contexts 512, 4096, 32768, and 131072 after chunked GEMV works. Check:

- whether a score Tensor proportional to `chunk * context` materializes
- peak allocation size
- attention share of prefill time
- decode degradation as valid context grows

Port tiled NVIDIA flash attention only if the generic path is the next measured bottleneck or violates memory bounds. Reuse the online-softmax structure already present in `kernels/amd.py`; do not add a dependency.

For Q8_K_XL with quantized KV, use the packed-cache attention kernel from priority 1 instead of building a separate half-cache implementation unless the profile justifies both.

## Phase 6 — Long-context scaling proof

Run sequentially:

| Prompt | Gate |
|---:|---|
| 512 | numeric and benchmark baseline |
| 4096 | chunking stability |
| 32768 | first attention/memory scaling gate |
| 131072 | sustained scaling |
| 262144 minus completion reserve | native-context proof |

At each size record pp, tg, peak VRAM, generated token/checksum, and cache reuse behavior. Stop on the first nonlinear allocation or incorrect output.

A full 262144-token prompt leaves no completion room. Reserve at least the requested output budget.

## Transfer to Q8_K_XL

Q4 has about 9 GiB free at full FP16 context; Q8 with quantized KV has less. After every Q4 optimization passes:

1. Run the same chunk size at Q8 context 4096.
2. Run Q8 at context 262144 with the selected quantized cache.
3. Require the priority-one peak budget: <42 GiB Q8_0 cache, <40 GiB Q4_0 cache.
4. Reduce chunk size only if measured scratch, not weight/cache baseline, consumes the margin.

## Service correctness checks

Before declaring practical serving complete:

- deterministic context-512 versus context-262144 first-token/logit A/B
- prompt+completion boundary: available-1, available, available+1
- missing completion limit caps at remaining context
- context exhaustion reports `finish_reason="length"`
- prefix reuse and divergent reset equal cold runs
- `make stop-tg` releases all GPU memory
